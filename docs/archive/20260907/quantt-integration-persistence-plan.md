## 2. 目标与边界

### 2.1 核心目标

将 QuantT 作为 Tickflow 内的独立垂直业务域接入，使其能够：

1. 复用 Tickflow 的证券基础信息、历史行情、复权、基准指数和涨跌停规则；
2. 持久化训练会话的每一步操作，刷新页面或重启后端后可准确恢复；
3. 无损承接原 QuantT 的训练、交易、画线、AI 点评、提示词及审计历史；
4. 与 Tickflow 的认证、API 错误处理、前端查询缓存和桌面打包方式统一；
5. 保持模块故障隔离，QuantT 不可用时不影响行情、策略、QuantX 等其他能力；
6. 建立可审计、可备份、可恢复、可继续演进的数据资产底座。

### 2.2 明确不做

本阶段不包含：

- 将训练数据转换成 Market Facts；
- 多用户、云端协同或 PostgreSQL 改造；
- 永久删除训练资产；
- 重构 AI 模型或提示词体系；
- 导入券商真实成交单；
- 迁移原 QuantT 的可丢弃行情缓存；
- 为假设中的未来功能提前建立通用工作流平台。

## 3. 当前状态与主要问题

### 3.1 Tickflow 可复用能力

Tickflow 当前已经具备：

- 以 Parquet 为主的行情与标准事实存储；
- `KlineRepository` 等统一查询入口；
- 内存 DuckDB 查询层；
- `DATA_DIR` 项目数据根目录；
- 后端 `backend/app/custom/<module>` 扩展机制；
- 前端 `frontend/src/custom/<namespace>/extension.tsx` 路由、导航和插槽扩展机制；
- FastAPI、TanStack Query、统一错误处理及桌面打包基础。

但 QuantT 接入仍需要三个小型核心扩展缝：

1. 稳定、只读的历史行情读取端口；
2. 前端扩展可使用的共享请求客户端和查询键约定；
3. 桌面打包时显式收集 `app.custom` 动态子模块。

### 3.2 QuantT 当前持久化风险

原 QuantT 已经把完成后的训练结果、动作、交易、画线、AI 点评、提示词产物和审计记录保存到 DuckDB，完成会话具有较好的可复现性。

主要缺口是训练过程中的实时状态仍以服务内存为主：新建会话、逐步操作和画线只有在完成训练后才形成完整结果快照。后端意外退出时，尚未完成的训练可能丢失；浏览器本地状态也不能成为权威恢复来源。

因此迁入 Tickflow 时，不能只搬页面和完成结果，必须先改造成逐步持久化的会话模型。

## 4. 总体架构决策

QuantT 应定位为 Tickflow 内的“垂直用户工作流域”，而不是：

- Market Fact；
- 数据提供方；
- 普通策略；
- `ext_data` 附属字段；
- 仅包含一张页面的轻量插件。

采用“扩展模块为主、最小核心接口为辅”的混合方案：

- 后端主体放入 `backend/app/custom/quantt/`；
- 前端主体放入 `frontend/src/custom/quantt/`；
- 运行数据放入 `DATA_DIR/training/`；
- 只在核心层增加必要的稳定端口、前端请求入口和打包发现能力；
- 避免长期直接修改 `backend/app/main.py`、`frontend/src/router.tsx`、`Layout.tsx` 等高冲突文件。

推荐数据流：

```text
行情提供方
    ↓
Parquet / KlineRepository
    ↓
HistoricalBarReader（稳定只读端口）
    ↓
QuantT TrainingService
    ├── TrainingRepository
    │       ↓
    │   DATA_DIR/training/training.duckdb
    ├── AI Review Service
    └── Profile / Statistics
            ↓
       /api/training/*
            ↓
         /training
```

页面至少包含：

## 6. 统一行情读取端口

新增只读 `HistoricalBarReader`，隔离 QuantT 与 Tickflow 内部表结构。端口至少提供：

- 标的列表和证券名称；
- 原始日线或指定周期行情；
- 不复权、前复权、后复权；
- 基准指数行情；
- 前收盘价；
- 涨跌停价格与板块规则；
- 数据来源、生成批次和覆盖范围；
- 可训练标的与可用历史长度。

实现应复用现有 `KlineRepository`、复权逻辑和涨跌停规则，禁止 QuantT 再建立独立行情采集流水线。

可训练标的缓存必须包含行情 generation 或等价版本信息；行情更新后缓存自动失效，不能长期保存过期资格结果。

训练会话创建后，实际使用的标的 K 线和基准 K 线应冻结保存到训练库中。该复制是为了训练可复现，属于有意的数据冗余，不应被后续行情回补或复权因子变化覆盖。

## 7. 持久化设计

### 7.1 权威数据库

目标数据库：

```text
DATA_DIR/training/training.duckdb
```

继续采用 DuckDB，保留原 QuantT V3 数据模型与语义，并增加未完成会话检查点和存储元数据。

新增建议表：

#### `training_checkpoint`

用于恢复未完成训练，建议包含：

- `session_id`；
- 当前播放位置和步骤号；
- 压缩后的领域状态；
- 状态版本；
- SHA-256 校验值；
- `created_at`、`updated_at`；
- 生命周期状态；
- 最近一次客户端请求 ID。

#### `storage_metadata`

用于记录：

- schema 版本；
- 迁移版本；
- 应用版本；
- 创建与升级时间；
- 最近备份和校验结果。

生命周期状态应使用单独字段或表表达，避免继续复用含义不同的 `record_status`。

### 7.2 写入时序

创建训练时：

1. 校验标的、时间范围和行情覆盖；
2. 获取并冻结训练 K 线、基准 K 线及关键元数据；
3. 生成初始领域状态；
4. 在一次事务内写入会话、冻结行情和首个 checkpoint；
5. 数据提交成功后才向前端返回会话。

每次动作或画线时：

1. 从内存状态复制出候选状态；
2. 在候选状态上执行操作；
3. 原子写入动作记录和新 checkpoint；
4. 提交成功后才替换服务内存状态并返回结果；
5. 写入失败时，界面进度不得前移。

完成训练时：

1. 幂等校验会话尚未完成；
2. 在同一事务写入最终结果快照、标准化交易和统计；
3. 标记生命周期为完成；
4. 删除对应 checkpoint；
5. 事务成功后触发画像刷新和可选 AI 点评。

### 7.3 恢复与幂等

- 后端启动时扫描有效 checkpoint，按状态版本和校验值恢复；
- 页面刷新后通过 API 获取权威状态；
- 所有写请求携带客户端请求 ID，重复提交返回同一结果；
- 完成、回收、恢复和 AI 任务创建均必须幂等；
- AI 点评在执行前先写 `pending` 记录，失败只更新点评状态，不能回滚训练结果；
- 删除继续采用软删除和回收站，不提供永久删除 API。

## 8. API 规划

建议统一放在 `/api/training`：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/sessions` | 创建并持久化训练 |
| `GET` | `/sessions` | 查询历史及未完成训练 |
| `GET` | `/sessions/{id}` | 获取完整可恢复状态 |
| `POST` | `/sessions/{id}/actions` | 提交训练动作 |
| `PUT` | `/sessions/{id}/drawings` | 保存画线状态 |
| `POST` | `/sessions/{id}/finish` | 幂等完成训练 |
| `POST` | `/sessions/{id}/trash` | 移入回收站 |
| `POST` | `/sessions/{id}/restore` | 从回收站恢复 |
| `POST` | `/sessions/{id}/ai-reviews` | 创建 AI 点评任务 |
| `GET` | `/profile` | 获取训练画像 |
| `GET` | `/storage/status` | 获取版本、迁移及备份状态 |
| `POST` | `/storage/backup` | 手动触发安全备份 |

接口应复用 Tickflow 的认证、统一错误格式和请求日志。领域错误需区分：行情不足、会话冲突、重复操作、存储失败、迁移未完成和 AI 服务不可用。

## 9. 原数据无损迁移

### 9.1 迁移源与目标

迁移源只读：

```text
D:\quantall\apps\quantt\data\training.v3.duckdb
```

迁移目标：

```text
DATA_DIR/training/training.duckdb
```

以下内容必须完整迁移：

- 会话与冻结行情；
- 基准行情；
- 训练动作；
- 交易和收益结果；
- 画线；
- AI 点评、调用记录和标签；
- 提示词 bundle、产物和审计记录；
- 回收站及生命周期状态。

以下内容禁止迁移：

- `%LOCALAPPDATA%\quantt\cache\market_cache.duckdb` 等可再生行情缓存；
- Token、密钥、`.env` 和本地 AI 配置；
- 临时日志、构建产物和测试数据库。

### 9.2 迁移流程

1. 停止原 QuantT 写入并将其切换为只读；
2. 对源库记录文件 SHA-256、schema、表行数、会话数和时间范围；
3. 对会话、点评和产物生成稳定内容哈希；
4. 在目标目录外的 staging 文件中执行 schema 创建与导入；
5. 运行表级、会话级和产物级对账；
6. 通过后再原子替换目标正式库；
7. 保存迁移 manifest、源库校验值、目标库校验值及执行日志；
8. 原系统保持只读观察 14 天，期间 Tickflow 是唯一写入方；
9. 观察期结束后另行决定归档，不自动删除源库。

历史审计中看到的行数和覆盖日期只能作为规划基线，正式切换前必须重新计算，不能把旧数字写死成验收条件。

## 10. 备份与恢复

默认备份目录建议放在项目运行数据之外：

```text
%LOCALAPPDATA%\TickFlowStockPanel\backups\training
```

并允许通过无密钥配置切换到另一块磁盘。

备份策略：

- 数据发生变化时，每日最多生成一个日备份；
- 保留最近 14 个日备份和 6 个按月备份；
- 备份前执行 DuckDB checkpoint；
- 每个备份包含数据库、manifest 和 SHA-256；
- 启动时和重要写入后检查备份状态，不新增常驻调度线程；
- 界面展示最近成功时间、路径、校验值和失败原因。

恢复策略：

- 不提供可误触的在线破坏性恢复 API；
- 通过离线维护命令恢复到 staging；
- 校验通过后，先为当前库建立恢复前备份，再原子切换；
- 恢复后执行 schema、行数、哈希和关键会话抽样验证。

## 11. 打包、升级与数据保护

### 11.1 桌面打包

PyInstaller 配置需要收集后端动态扩展：

```python
collect_submodules("app.custom")
```

否则源码运行正常的 QuantT 可能在桌面包中消失。必须分别验证源码、Docker 和桌面打包三种运行形态的扩展发现。

### 11.2 数据保护

必须建立回归保护：

- Tickflow 的“清理数据”能力不能删除 `DATA_DIR/training/`；
- 覆盖安装和版本升级不能覆盖训练库；
- 行情全量重建不能修改已冻结的历史训练样本；
- 原 QuantT 和 Tickflow 不得同时写同一份或两份活跃训练库；
- 数据目录内的数据库、备份和迁移产物不得进入 Git。

当前服务为单 worker，可使用进程内写锁串行化 DuckDB 写入；每个操作使用短生命周期连接和事务，不长期持有数据库连接。若未来改成多 worker 或多进程，再单独设计写入代理或外部数据库，不在本阶段预先实现。

## 13. 验证矩阵

### 13.1 数据与算法

- 原始、不复权、前复权、后复权逐字段比对；
- 前收盘、涨跌停、基准指数逐日比对；
- 各抽样模式、市场板块和时间范围结果比对；
- 历史不足、停牌和异常行情边界测试；
- 行情 generation 更新后的资格缓存失效测试。

### 13.2 持久化与恢复

- 创建后立即刷新页面；
- 每种动作后刷新页面；
- 画线后刷新页面；
- 后端正常重启与强制终止后恢复；
- 模拟 DuckDB 写入失败，确认前端步骤不前移；
- 重复请求、重复完成和重复迁移保持幂等；
- 行情重新同步后，旧训练内容与结果不变；
- AI 失败不影响训练保存；
- 回收站移入和恢复完整可逆。

### 13.3 迁移与备份

- 源目标 schema、行数、会话和产物哈希对账；
- 随机抽样历史训练可完整回放；
- 备份校验、保留策略和跨目录恢复；
- 恢复前备份及 staging 原子切换；
- 数据清理、更新和覆盖安装不触碰训练数据。

### 13.4 应用集成

- QuantT 扩展故障不影响其他页面和 API；
- 源码、Docker、桌面包均能发现扩展；
- 后端相关测试和前端构建通过；
- UI 改动使用独立 Playwright 和 Microsoft Edge headless 验证；
- 关键训练流程覆盖端到端测试和截图证据。

## 14. 完成验收标准

只有同时满足以下条件，才能声明迁入完成：

1. 原 QuantT 权威数据全量对账，无未解释的缺失或重复；
2. 未完成训练可在页面刷新、服务重启和异常退出后准确恢复；
3. 每个动作先持久化后反馈，存储失败不会产生假进度；
4. 历史训练不受未来行情修订影响；
5. AI 失败不会破坏训练主链路；
6. 备份和恢复完成真实往返验证；
7. 数据清理、升级和打包均不会遗漏或误删 QuantT；
8. 源码、Docker 和桌面包验证通过；
9. 旧 QuantT 已冻结只读，Tickflow 是唯一写入方；
10. 观察期内无数据差异和阻断问题。

## 15. 后续执行约束

后续以本文创建 Goal 时，应坚持以下顺序：

```text
先冻结与审计
  → 再完成存储和迁移工具
  → 再接行情适配与训练引擎
  → 再接 API 和前端
  → 最后执行正式迁移与切换
```

不得先复制页面后补持久化，也不得让旧 QuantT 与 Tickflow 同时写入。任何正式迁移、数据库 schema 变更、源库切换或旧目录归档，都必须在执行前重新检查当前数据并建立备份。

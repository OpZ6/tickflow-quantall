01结论速览

先给结论，细节在后面逐节展开。

  • AI 分析不是没做，是全被一个开关关着。全项目共有 10 个 AI 相关能力点（1 个交互式助手、4 类报告生成、3 类代码/信号生成、1 套配置基础设施、1 份 LLM 报告契约），另有 1 组「名字像 AI 其实是纯算法」的模块已单独排除。会真正调用 LLM 的链路全部走同一个 backend/app/services/ai_provider.py，而 ai_configured() = false，所以当前没有任何一条链路能真正调用 LLM。
  • 数据层完全健康。本次为每个点拉取依赖的只读上下文，25 个端点 全部 HTTP 200，合计约 8.3 MB 真实数据（含 20261104 全市场 5571/5572 只标的快照、涨停梯队、情绪状态、397 概念轮动矩阵、股票池 503 候选、QuantX 7 段复盘数据等）。缺的只是那把 key，不是数据。
  • 根因是一行键名。.env 里写的是 deepseek-api-key=sk-5fd…，而 app/config.py 读取的是 AI_API_KEY，从未被加载。用项目自带的无副作用探测接口 POST /api/settings/ai/test 实测该 key 返回 {"ok":true,"response":"OK"}，key 有效。
  • 接上之前先修数据口径。实测发现 7 组指标在两套数据源之间不一致（涨停 122 vs 118、封板率 77.2% vs 78.1%、情绪 83「强势」 vs 62「偏热」等），另有板块轮动数据时间戳滞后到 2026-09-02、涨停股 002578 本地财报覆盖为 0。这些会让任何 LLM 报告建立在不同口径甚至缺失数据上 —— 详见第 5 节。
  • 「让我获取上下文解答」已验证可行。第 3 节每个能力点都附了一段 本次由 WorkBuddy 直接读取上下文生成的代答（非项目 LLM 产物），并标出该点当前的实际可用性。
本报告只做只读探查与上下文拉取：未修改任何配置、未启用付费 API、未触发任何 LLM 生成接口。所有 POST 类生成端点均未调用。

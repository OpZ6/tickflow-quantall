00 / 结论

先建立正确的心智模型

TickFlow 不是“一个爬虫加一个网页”，而是一个小型市场数据平台：先把外部世界翻译成稳定事实，再由确定性逻辑生成分析，最后由 API 把结果交给页面。

数据底座越丰富，未来功能确实会越简单；但真正带来复用的不是“数据多”，而是“数据有契约、有质量、有时间语义、能稳定读取”。否则每个页面仍要重新猜字段、补空值、处理日期和修供应商变动，数据再多也只会形成新的孤岛。
1
物理分散，逻辑统一
K 线、市场事实、扩展表可以分开存，但必须从 Repository 稳定读取。
2
来源不等于事实
供应商返回只是原料；标准化、质量验证和发布后才成为可复用数据。
3
页面不是计算中心
页面负责交互与表达，不负责抓取、猜单位或复制后端算法。
4
兼容层正在收口
QuantX JSON 与旧 scraper 仍存在，但已被统一入口包住，不再是新开发入口。
01 / 分层

三层架构：每层只回答一类问题

判断一个新需求应该放在哪里，最简单的方法是问：它是在描述世界、解释世界，还是把结果讲给人看？

DATA数据层
来源连接字段翻译单位统一分区存储质量与溯源稳定读取
回答“发生了什么”。不包含图表颜色、页面文案和策略判断。
LOGIC处理层
指标筛选策略回测市场状态QuantX 单日 / 多日
回答“这意味着什么”。输入显式、窗口明确、结果可重复。
VIEW展示层
FastAPISSE查询缓存页面状态图表交互
回答“用户怎样理解和操作”。不直接碰供应商或任意本地文件。
依赖方向只有一个：展示依赖处理，处理依赖数据。下层永远不应反向 import 页面类型或为了某张图改变事实含义。
02 / 入口

为什么有两条数据入口，而不是一个万能插件

规则行情和非规则市场事实的形状、刷新频率与质量判断完全不同。强塞进一个接口会让契约变得含糊，因此 TickFlow 使用两条互补轨道。

〽
行情轨道

Market Data Provider

适合可被统一描述的价格、成交、复权、分钟、实时和财务数据。

选择来源内置服务、简单 HTTP 配置或 Python / Node 插件
翻译为内部行情语义统一证券代码、日期、价格、成交量和比例口径
写入行情仓库按资产与日期分区，并生成 enriched 分析底表
供所有业务复用策略、回测、监控和页面不再关心供应商
◎
事实轨道

Source Manager + Market Facts

适合涨停事件、题材、行业资金流、宽度、市场状态等非 K 线事实。

注册来源说明声明依赖、凭据引用、超时、重试、新鲜度和角色
隔离采集失败认证、限流、网络、解析等失败被稳定分类
构建标准事实原始证据经过规范化、质量校验与来源优先级选择
原子发布完整新版本一次替换；失败时继续保留上一版

这份新数据，本质上是什么？

入口类型一条记录代表什么必须保留的语义最适合的交换格式

分钟行情一个证券在一个分钟时点的价格与成交摘要证券、资产类型、北京时间、周期、价格与成交；股票 / ETF / 指数分开路由HTTP / 插件输入，按资产和日期 Parquet

YAML 自定义源

描述“怎样请求与怎样翻译”

配置只表达来源名称、认证引用、接口位置、请求方式、批量与限速、数据所在路径、供应商字段到内部语义的映射，以及日期或单位变换。密钥只引用环境变量，不写进配置。

Provider 插件

描述“我具备哪些能力”

插件清单声明身份、运行时、入口、依赖探测和支持的数据类别；实现负责复杂签名、分页、SDK 调用与标准化。未安装插件时只显示不可用状态，不影响主程序启动。

03 / 存储

数据怎样落盘：不是一个大数据库

主存储采用 Parquet 文件，按数据集和交易日组织；DuckDB 更像高速查询引擎，不是唯一主库。JSON 主要承担原始证据、运行清单和 QuantX 展示兼容。

事实与行情的主载体

列式压缩、适合按列扫描和批量计算；按日期分区后可避免每次读取全历史。

DuckDB

查询加速层

把多个 Parquet 分区注册成统一视图，提供 SQL 范围查询；文件仍是持久化权威。

JSON

证据与兼容载体

04 / 契约

丰富数据底座的真正核心：Dataset Contract

一份数据只有同时回答“它是谁、每列什么意思、按什么时间分区、来自哪里、缺失怎么办”时，才能安全地被多个功能复用。

🪪

身份

稳定数据集名称、版本、主键和分区方式，保证同一事实不会被不同页面重新命名。

⚖

口径

百分数与比例、金额数量级、复权与原始价格、北京时间与交易日全部显式说明。

🧭

来源路由

主来源、备用来源与质量等级是契约的一部分，页面不自行决定“哪个网站更可信”。

🧾

溯源

每批数据保留来源、观测时间、采集时间、运行批次、版本和是否降级。

🧪

质量

必填、重复、日期错位、最小记录数、空数据和新鲜度在发布前检查。

🕰

时间正确性

多日窗口按真实交易日；缺日保持缺失，不能用零、未来值或另一天的数据伪造。

05 / QuantX

QuantX 独立更新流水线：从网页原料到单日 / 多日面板

它不依赖原 QuantX 报告服务，也不包含 LLM 分析。网络采集、确定性计算、标准事实和展示缓存都在 tickflow-quantall 自己的数据目录内完成。

01计划确定交易日与来源集合
02采集复用快照或隔离网络访问
03规范化供应商形状转内部语义
04计算单日表与多日确定性结果
05质检来源与事实契约双重验证
06发布事实与日期快照原子替换

Source Manager 做了什么

  • 所有来源先注册，名字不能重复
  • 依赖缺失不拖垮其他来源
  • 失败稳定区分为认证、依赖、限流、超时、网络、解析、缺失、过期等类型
  • 单个来源按契约重试，支持只重试失败源
  • 重算模式只读本仓库快照，不访问网络
  • 新鲜度不匹配时明确标记 stale，而不是伪装成功

发布为什么可靠

  • 先在临时运行区构建完整新版本
  • 标准事实先 stage，并生成行数、大小与哈希
  • 只有 complete 或 degraded 才允许进入发布
  • 目标文件先备份，再用原子替换切换版本
  • 任何一步失败都会回滚，旧版本继续可读
  • 发布成功后再刷新多日快照与日期目录

运行状态不是只有“成功 / 失败”

COMPLETE完整必需来源和事实满足契约
DEGRADED降级可用备用来源生效，质量信息随数据传递
FAILED未发布保留上一份有效数据，不暴露半成品
RECOMPUTE离线重算用本地快照重建处理结果，避免来源漂移
仍然存在的兼容边界：legacy_scrapers 目录里的供应商实现仍被使用，但它们只能由 Source Manager 调度；QuantX 日期 JSON 仍服务富图表与旧接口，但可复用事实会由 Market Facts 和行情仓库覆盖。它们是受控适配层，不是未来新功能的入口。
06 / 处理

处理层如何把事实变成能力

处理层不是一个巨型脚本，而是按复用范围拆为指标、服务、策略、回测和 QuantX 计算。共同原则是：只读稳定 Repository，输出可测试的确定性结果。

指标流水线

向量化

把窄行情表计算成均线、动量、波动、量价、涨跌停等 enriched 分析底表，供多个业务共享。

领域服务

编排

组合多个 Repository，处理市场状态、情绪、轮动、同步、监控与缓存，不负责供应商解析。

策略引擎

18 策略

统一注册、参数、筛选、评分和结果契约；内置与自定义策略共享执行边界。

回测

防未来函数

信号生成与成交模拟分离，显式执行 T+1、成本、滑点和不可成交约束。

QuantX 单日

富图表

把当日事实编排成市场、涨停、题材、行业、资金与候选等可视化区域。

QuantX 多日

交易日窗口

基于历史标准事实构建信号矩阵、连续性、热力图和机会雷达，缺日降低覆盖率而不是补零。

enriched 的关键价值：它把“每个策略都自己算一遍技术指标”变成“统一计算一次，多处复用”。这正是丰富数据底座让未来开发变简单的真实例子。
07 / 展示

API 与前端：把稳定结果翻译成用户体验

09 / 可靠性

为什么“文件写成功”还不等于页面更新成功

系统同时有持久化、Repository 内存、计算版本、服务缓存、SSE 与浏览器查询缓存。一次更新要贯穿整个失效链。

一次完整写入需要照顾五层状态

① 磁盘事实

分区文件或日期快照完成原子替换

② Repository

内存对象重读或 generation 更新

③ 业务缓存

策略、筛选、矩阵等缓存键失效

④ 推送事件

必要时通过 SSE 告知在线页面

⑤ 前端查询

精确 invalidation，保留旧值到新值就绪

故障原则

新版本不完整时保持旧版本，不短暂展示空白

一天的数据生命线

盘前标的、能力与任务准备
盘中实时快照和增量聚合
收盘后日线、复权、指标、事实采集
质量门完整 / 降级 / 失败判定
发布后缓存刷新、目录更新与页面读取
10 / 开发

未来如何加入新数据、新分析和新页面

不要从“我要画一张图”开始写。先确定输入事实是否存在，再沿 Repository → 纯计算 → Service → API → 前端单向接线。

PATH A

接一个自有 HTTP 行情源

适合已有简单 REST 接口的日线、实时、分钟、复权或财务数据。

写来源配置 → 映射语义与单位 → 试拉 → 选择路由 → 小范围同步 → 核对落盘与页面
PATH B

接一个复杂行情 SDK

适合签名、分页、专有依赖或 Node 桥接。

插件清单 → 可用性探测 → Provider 实现 → 能力声明 → 注册 → 契约测试
PATH C

增加一种市场事实

适合北向流、公告事件、产业链热度等跨页面复用数据。

确认不可复用现有事实 → 固化样本 → 定义契约与来源 → builder → 发布 → Repository
PATH D

增加指标或分析

输入已经存在，只需新的确定性解释。

Repository 范围读取 → 纯函数 → 边界测试 → Service 缓存 → API → 页面
PATH E

增加一个图表或面板

不应引入新的供应商读取或在浏览器复制算法。

复用 API 或新增薄接口 → 精确前端类型 → query key → 组件 → 六态验证
PATH F

增加用户自己的辅助字段

只为自定义列、标签或外部表服务，不值得升级为公共事实。

ext_data 导入 / 拉取 → 选择快照或时序模式 → 配置展示 → 核对主键与刷新

一个完整功能的 Definition of Done

阶段必须回答最低证据
数据来源、单位、日期、主键、空值、备用来源是什么？固定样本 + 契约测试
处理窗口如何定义？缺日怎样处理？是否可能使用未来数据？最小 / 正常 / 缺失 / 边界测试
接口成功、无数据、降级和失败如何表达？Service 与 API 测试
展示加载、空、错、禁用、过期、降级是否清晰？构建 + Playwright 页面、控制台和网络检查
发布写后哪些缓存要失效？失败是否保留上一版本？原子发布 / 缓存一致性测试
11 / 评估

现在是否已经达到“数据、处理、展示清晰分离”

结论不是简单的“是 / 否”：核心骨架已经成立，开发规范也已经明确；但少量兼容链路仍需继续迁移，才能让所有功能都享受同一数据底座。

架构成熟度（基于当前实现的工程判断）
78/100

主干依赖方向、两类数据入口、标准事实、原子发布、Repository 和前端查询边界都已落地。扣分主要来自 QuantX 兼容 JSON、遗留来源适配器和部分历史数据 / 页面仍可能存在专属逻辑。

已经清晰通用行情 Provider、标准事实 Registry、Repository、处理模块、API、前端类型与查询键。
渐进收口QuantX 日期 JSON 仍承担富图表兼容；应继续让可复用字段以 Market Facts 为权威。
受控遗留旧 scraper 仍是真实采集适配器，但业务层已被禁止直接调用。
下一阶段重点扩大标准事实覆盖、统一质量与覆盖率展示、减少展示缓存中的重复事实、建立血缘和刷新可观测面板。
你的理想是可行的：当新需求所需输入已经在标准 Repository 中，新增分析通常只剩“纯计算 + 薄 API + 图表”三件事。真正要持续投资的是数据契约、历史覆盖、来源冗余、质量监控和缓存一致性，而不是无限增加页面专属抓取。

建议的演进顺序

1. 扩事实补齐高复用数据集与历史
2. 收兼容逐项移除 JSON 重复权威
3. 显质量页面统一展示覆盖率与来源
4. 建血缘从图表反查事实与运行批次
5. 提模板新事实 / 新分析脚手架自动化
12 / 上游

如何继续跟踪 TickFlow 原项目而不丢失 Quantall 能力

独立仓库保留两个远端：origin 是你的稳定分叉，upstream 是原作者只读来源。同步使用临时集成分支和 merge，不在脏工作区直接合并。

上游原项目只读 fetch，优先正式 tag 或明确 commit
→
只读预检共同基线、双方提交、重叠热点、文本冲突
→
sync 临时分支理解双方语义，逐文件解决冲突
→
完整回归后端、前端、契约与关键页面
→
origin/mainPR 合并，保留双方历史，不 force-push
高风险重叠区：应用启动、盘后任务、数据源路由、策略引擎、前端路由与布局、API 类型、查询键和依赖清单。QuantX 隔离目录通常更少冲突，但只要触及共享管道就必须跨模块回归。

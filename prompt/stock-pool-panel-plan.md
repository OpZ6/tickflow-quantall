# 九召回池统一面板：完整实现与召回收敛计划

更新日期：2026-09-15。

## 一、产品目的

本面板服务个人主观实盘复盘。每天收盘后把全市场五千余只股票压缩成一份可解释、可继续缩小的观察名单，回答四个问题：

1. 为什么今天值得看这只股票；
2. 它目前处于哪个演化阶段；
3. 哪些状态提高或降低今日关注顺序；
4. 这个观察理由何时过期或失效。

它不是成熟量化策略，也不直接输出买卖动作、仓位或收益概率。历史收益研究用于判断哪些条件适合成为召回理由、排序信息或失效条件，不能因为某个粗池没有独立稳定超额，就删除它的发现价值。

第一版保留九个召回入口，板块轮动不再独立召回。行业、概念、市场环境和热度仍可以作为背景、标签或后续验证的权重。

## 三、九个召回器

以下是第一版工程口径。参数全部版本化；召回器保存完整命中，不在内部用固定名额截断。

| ID | 名称 | 召回意义 | 第一版边界 | 原始有效期 |
| --- | --- | --- | --- | --- |
| `pool_breakthrough` | 突破 | 趋势或价格发现启动 | 当日最高价或收盘价突破此前60／100／250日高点，保留突破类型 | 最长10日，失守锚点提前结束 |
| `pool_limit_ladder` | 涨停梯队 | 强势正在发生 | 按当日真实涨停事实识别封板及板位 | 当日，次日转入其他阶段 |
| `pool_abnormal_surge` | 异动 | 短期快速聚集注意力 | 首次跨过10日30%或30日50%，记录是否达到10日80%及当日封板状态 | 最长3日，极端非封板正向观察仅1日 |
| `pool_liquidity_trend` | 趋势 | 高流动性趋势载体 | `close > MA20 > MA60`、MA20向上、距高点不过深、成交额前200 | 每日重算，离榜或趋势破坏即结束 |
| `pool_divergence` | 分歧 | 首／二板后进入承接检验 | 近1—3日首板或二板，当日非涨停，保留回调深度、锚点低点和收盘位置 | 3日，破锚点立即失效 |
| `pool_failed_limit_repair` | 炸板修复 | 触板失败后的修复尝试 | 近1—3日真实炸板，记录是否守低点、缩量、收涨和重新封板 | 3日，正向注意力以事件后1日为主 |
| `pool_trend_pullback` | 趋势回踩 | 启动后的回调阶段 | 近5—20日存在突破或启动事件，仍在主要趋势上，触及MA10／20附近 | 3日，失守趋势或放量破位即结束 |
| `pool_active_character` | 股性活跃 | 近期资金记忆和活跃基因 | 近10日涨停或近30日多次涨停，保留最近事件、次数和当前趋势状态 | 每日重算；涨停后第1日单独标记 |
| `pool_popularity_warm` | 人气中温 | 外部关注度补充发现 | 至少一个可信个股热度来源进入约20—100名，保留来源重叠和排名变化 | 当日，无数据时为`unavailable` |

研究结论与产品召回的关系：

- 突破、涨停、异动等事件可以提供独立召回理由；
- 趋势、回踩、分歧、炸板和股性即使长期超额不强，也可以发现处于特定阶段的股票；
- 历史上只体现状态价值的条件先降低优先级，不直接获得高分；
- 人气数据覆盖不足时保留入口和字段，不伪造候选；
- 板块轮动只给已召回股票提供环境信息，不产生第十个来源。

## 四、正式数据架构

正式面板不能继续读取研究账本或任意`data/quantx/YYYYMMDD/*.json`。稳定调用链为：

```text
行情 Provider
  -> KlineRepository / enriched日线

QuantX SourceManager
  -> SourceSnapshotStore
  -> Market Facts
     - limit_event_daily
     - limit_ladder_daily
     - 后续 security_popularity_daily

Repository输入
  -> 九个召回器
  -> 去重与来源事件合并
  -> 阶段、有效期和失效判断
  -> 每日股票池派生快照
  -> StockPoolRepository
  -> FastAPI
  -> React面板
```

数据分类：

| 数据 | 权威位置 |
| --- | --- |
| OHLCV、均线、量比、滚动高点、成交额 | `KlineRepository`及enriched分区 |
| 涨停、跌停、炸板、连板高度 | `MarketFactRepository` |
| 个股人气排名 | 新增SourceManager来源及标准事实；缺失保持未知 |
| 原始召回事件 | 复用`strategy_signal_events`保存版本、事件日和锚点 |
| 每日去重名单、阶段和有效期 | 股票池专用派生快照及Repository |
| 页面筛选、排序和详情 | API响应，前端不重新计算业务规则 |

不直接扩写QuantX展示缓存。现有`screening_candidate_daily`可以提供部分候选字段，但不足以表达多来源、事件锚点、阶段、年龄和过期原因；实施前应评估是升级该契约，还是新增专用派生快照。优先选择影响现有QuantX消费者更小的方案。

### 与QuantX共用数据基础，不建立股票池特例

股票池是新的业务面板，不是新的数据框架。它与QuantX平级展示，但底层必须使用项目已有的通用采集、事实、Repository、发布和查询链路：

```text
外部来源 / 行情Provider / 已发布Research
  -> SourceSpec或明确的上游Repository
  -> SourceSnapshotStore（保留原始证据、观察时间和来源状态）
  -> normalizer / builder
  -> Market Facts或对应的通用领域Repository
  -> 股票池确定性派生计算
  -> 日期级原子快照与manifest
  -> StockPoolRepository
  -> FastAPI
  -> React + TanStack Query
```

正式实现遵守以下边界：

- 前端和API不直接请求同花顺、雪球、百度、东财、Fuyao或SMNC；
- API不直接读取`data/quantx/<date>/*.json`、研究账本、原始采集JSON或另一项目目录；
- `legacy_scrapers`只允许作为SourceManager背后的供应商适配层，股票池业务代码不导入它；
- 页面所需的日期、来源覆盖、规则版本、输入generation和降级原因随每日快照一起发布；
- 外部来源失败保留原始失败状态，可用事实继续发布，页面不把未知解释为零；
- 同一份人气、题材成员、涨停事件和逐股事件解释应能被QuantX、股票池及后续页面共同查询，不复制成股票池私有缓存；
- 股票池专属的多源合并、主阶段、有效期和个人注意力排序属于派生业务结果，保存在StockPoolRepository，不反向污染通用市场事实。

“通用接入”不等于把所有内容塞进一个Dataset。按语义分类：

| 数据 | 通用接入位置 | 股票池用法 |
| --- | --- | --- |
| OHLCV、复权、均线、成交额、换手 | 行情Provider与KlineRepository | 九池确定性计算和基础过滤 |
| 涨停、炸板、连板高度与涨停理由 | SourceManager + Market Facts | 涨停、分歧、炸板及当日题材证据 |
| 多源个股热榜 | 新增通用`security_popularity_daily`事实 | 人气召回、排名变化和来源覆盖 |
| 当日逐股异动解释／热点理由 | 新增可复用的事件解释事实，保留原文和观察时间 | 交易题材归类及详情证据 |
| 题材观察与股票成员 | `theme_observation_daily`、`theme_member_daily` | 当日题材聚类和静态关联；按时点读取 |
| 完成态Research／SMNC | 由publication manifest驱动的通用Research索引Repository | 定向公司检索和题材背景 |
| 九池来源事件、阶段、有效期 | StockPoolRepository派生快照 | 工作台、完整候选和跨日变化 |

Research材料已有自己的完成态、审计和publication manifest语义，适合建立通用Research索引Repository；不应为了形式统一而伪装成行情事实。它仍使用同样的版本、原子发布、只读Repository和可追溯原则。

### 个股人气数据

人气是唯一明显的新数据源负担。需要定义`security_popularity_daily`一类的标准事实，至少包含：

```text
trade_date
symbol
source
rank
rank_bucket
previous_rank
rank_change
observed_at
source_record_id
quality_level
```

同花顺可作为第一主源，雪球、百度或其他稳定来源作为补充。东财只有在真实接口和时点口径验证后接入。网页来源的失败不能阻断其余八池发布。

## 五、每日更新流

自动和手动更新统一执行：

```text
1. 盘后行情同步
2. 复权因子及enriched增量计算
3. QuantX来源采集与Market Facts原子发布
4. 九池按最新已发布交易日运行
5. 合并同股多来源，解析事件锚点和有效期
6. 与前一交易日快照比较，生成新增、延续、迁移、失效和退出
7. 质量校验通过后原子发布股票池快照
8. 清理查询缓存，前端跳转最新交易日
```

接线位置放在主行情成功、QuantX完成之后。手动`POST /api/pipeline/run`和定时盘后任务必须走同一函数，任务结果增加`stock_pools`状态。

还需覆盖三条恢复路径：

1. `recompute`只读取本地已发布行情和来源快照，重新计算股票池，不访问网络；
2. QuantX单来源retry成功后，自动重建相同日期的股票池；
3. 人气或其他可选来源失败时，以`degraded`发布八池结果，并明确缺失来源。

同一交易日单写入者，先写临时目录，完成数量、主键、来源和日期检查后再原子替换正式快照。不得让页面读取半成品。

## 六、每日快照契约

每只股票每天只产生一条聚合记录：

```text
trade_date
symbol / name
source_tags[]
source_events[]
  - source_id
  - event_date
  - latest_trigger_date
  - event_age
  - anchor_price
  - expires_on
  - invalidation_reason
primary_stage
state_tags[]
context_tags[]
risk_tags[]
priority_tier
freshness
evidence[]
data_quality
```

必须把`source_tags`和`primary_stage`分开。一只股票可能因为突破进入名单，三天后处于回踩；突破仍是来源事件，回踩是当前状态。

日期级汇总另存：

- 全市场数量、原始命中数、去重数和重叠数；
- 各来源命中、新增、延续、到期和失效数量；
- 各阶段当前数量；
- 各层级数量；
- 数据来源完整度和降级原因；
- 相对前一日的迁移边。

## 七、阶段推移地图

第一版逻辑地图：

```text
活跃记忆
   -> 突破启动 -> 趋势延续 -> 异动加速 -> 涨停强化
          |            |                         |
          v            v                         v
       回踩整理 <-------+-------------------- 高位分歧
          |                                      |
          +--------------> 企稳修复 <-------------+
                                  |
                                  +-> 再次突破

任意阶段 -> 失效／到期／退出观察
```

地图同时提供两种含义，界面必须明确区分：

1. 逻辑地图：显示理论上允许的演化路径；
2. 真实迁移：根据相邻交易日快照统计实际流量。

第二个交易日起可以显示当日迁移数量；积累20—60个交易日后再显示迁移比例、阶段停留中位数和典型路径。没有连续数据前，不把逻辑箭头解释为统计规律。

## 八、API与页面

建议独立路由：

```text
/stock-pools
/stock-pools/:date
```

建议API：

```text
GET /api/stock-pools/catalog
GET /api/stock-pools/{date}/summary
GET /api/stock-pools/{date}/candidates
GET /api/stock-pools/{date}/transitions
GET /api/stock-pools/{date}/{symbol}
```

候选接口支持来源、阶段、层级、新增／延续／临近到期、是否多池重叠、文本搜索、排序和分页。

页面结构：

1. 顶部：交易日、更新状态、数据完整度、去重数、新增数、到期数；
2. 九张召回卡：命中、新增、重叠、降级状态；
3. 阶段地图：当前分布和真实迁移两种视图；
4. 注意力层级：今日新增、核心关注、重点观察、完整候选；
5. 全量表格：一行一股，显示来源、阶段、年龄、有效期和证据；
6. 详情抽屉：事件锚点、阶段历史、状态变化、行情预览和数据质量。

复用QuantX的日期选择、刷新任务、TanStack Query缓存失效、股票预览和视觉规范。股票池保持独立页面，避免继续扩张QuantX主面板。

## 九、如何解决召回过多

召回过多不能只靠不断增加技术条件。目标是同时控制三件事：当天新进入多少、已有候选停留多久、最终需要人工仔细查看多少。

### 9.1 保留四层名单

建议把“全量召回”和“最终注意力”分开：

| 层级 | 作用 | 初始规模目标 |
| --- | --- | ---: |
| 原始命中 | 审计每个召回器，允许重复 | 记录全部 |
| 完整候选 | 按股票去重，保留全部来源 | 约150—400，暂不设硬上限 |
| 重点观察 | 事件仍新鲜、状态未失效、流动性合格 | 约50—120 |
| 核心关注 | 当日新增、关键阶段变化或少量高优先级 | 约20—50 |

规模是注意力目标，不是策略配额。第一阶段通过排序和分层达到目标，不在召回器里机械截断。完整候选始终可展开，方便检查遗漏和错误淘汰。

### 9.2 先解决驻留膨胀

0911最大的两个来源是股性活跃223只和趋势回踩111只。它们更像持续状态，容易让股票反复留在池里。优先研究：

- 每日新增数量与存量数量分别是多少；
- 单只股票连续驻留天数分布；
- 到第2、3、5、10日后仍保留多少有效信息；
- 失守事件低点、趋势位或流动性门槛后是否应立即退出；
- 同一事件刷新是否真的带来新信息，还是只重置年龄。

先收紧有效期和刷新规则，通常比增加更多入池指标更直接。持续状态可以继续作为标签，但不必每天重复占用核心关注名额。

### 9.3 再处理重复召回

多池重叠不代表应该多次加分。需要建立来源族：

```text
强势事件族：突破、涨停、异动
涨停记忆族：涨停梯队、分歧、炸板修复、股性活跃
趋势状态族：趋势、趋势回踩
外部关注族：人气中温
```

同族重叠主要表达同一事实的不同阶段，只保留最有时效性的证据；跨族重叠才作为额外信息展示。重叠加权必须在同日、相近基础状态下证明有增量，不能简单按命中池数累加。

### 9.4 硬过滤只处理基础不可观察性

第一版硬过滤限于明确且可追溯的条件：

- 当日停牌、无成交或关键行情缺失；
- 无法满足最低流动性的股票；
- 已退市或尚未上市；
- 根据当日可得事实识别的ST、特殊涨跌幅和不可交易状态。

历史ST和上市状态没有完整时点事实时标记质量降级，不能用今天的名称倒推过去。趋势、量比、回踩深度和人气等条件先用于排序，不急于作为全局硬过滤。

### 9.5 用淘汰成本评估每条收敛规则

每条候选规则或失效规则都报告：

```text
原始规模
-> 保留规模
-> 每日规模中位数和拥挤日P90
-> 大涨候选保留率
-> 次日及1／2／3／5／10／20日路径变化
-> 左尾变化
-> 年度和市场环境稳定性
```

这里的收益用于检查“删掉了什么”，不是把面板变成自动交易策略。若一条过滤只能提高均值，却漏掉大量后续强势股，应该降级为排序或风险标签。

### 9.6 排序优先于一刀切

第一版排序只使用可解释组件：

- 新鲜度：当日新触发、阶段刚变化优先；
- 事件性：突破、涨停、极端异动等新事件优先；
- 状态健康度：是否失守锚点、趋势位和关键低点；
- 跨族确认：价格事件与流动性、人气或板块环境是否同时出现；
- 可观察性：成交额、非一字、数据完整；
- 拥挤风险：极端涨幅、爆量、高位连续一致性适当降级。

页面展示组件分和证据，不输出“上涨概率”。排序版本与召回版本分开，便于回看某次变化究竟来自召回还是排序。

## 十、召回收敛的执行顺序

### 阶段A：冻结全量基线

先连续保存至少20个交易日的九池全量结果，不调整召回阈值。建立以下基线：

- 每日各池新增、存量、退出和去重规模；
- 事件年龄与驻留时间；
- 各池及交集对完整名单的边际贡献；
- 各阶段迁移和退出去向；
- 每天人工实际打开、标记和继续跟踪的股票。

人工使用行为很关键：面板目标是减少注意力，真正被打开、收藏、忽略和次日继续查看的记录，比单一未来收益更接近产品目标。

### 阶段B：先收有效期

依次检验：

1. 股性活跃只把新事件和涨停后第1日放入重点层，其他成员留在完整层；
2. 趋势回踩超过3日不再占重点层，发生新突破才重新激活；
3. 突破区分首次触发与重复刷新，刷新不自动重置全部有效期；
4. 分歧、炸板修复在破锚点、放量破位或超过3日后退出重点层；
5. 趋势池离开成交额和趋势条件后当日失效，不做额外驻留。

每一步单独发布规模变化，避免同时改多条规则后无法解释结果。

### 阶段C：研究来源的边际召回价值

对每个池分别回答：

- 它独立新增了多少其他池没有的股票；
- 独有候选中有多少最终被人工关注；
- 删除该来源会漏掉多少后续显著机会；
- 它是否只适合作为其他来源的状态标签；
- 与其他来源重叠时是确认、阶段转换还是重复信息。

只有独有召回贡献很低、人工使用率低、未来机会保留也低的来源，才考虑取消独立召回身份。

### 阶段D：收紧单池边界

完成有效期和重叠治理后，再研究阈值：

- 突破：盘中新高与收盘新高、60／100／250日、首次与重复突破；
- 趋势：成交额前50／100／200与稳定在榜；
- 回踩：MA10／20、突破年龄、缩量和失守；
- 股性：最近涨停年龄与30日次数；
- 异动：30%、50%、80%及是否封板；
- 分歧／炸板：事件板位、年龄、破低和量能；
- 人气：来源、排名区间、升温和多源重叠。

每次只改变一个有机制解释的维度。已经用于选条件的历史不再作为独立验证，冻结后由新增日期前向确认。

### 阶段E：设定个人注意力预算

当数据积累稳定后，再决定默认页面规模，例如：

- 今日新事件：不设名额，全部展示；
- 核心关注：目标20—50只；
- 重点观察：目标50—120只；
- 完整候选：全部保留，可搜索和复盘。

超过预算时先降低老旧、同族重复和已失效候选的层级。只有在长期拥挤且排序无法解决时，才考虑对某一宽池设置召回上限。

## 十五、具体主题与个人处理流程优化（2026-09-14，Demo已实现）

- **层次导航**：对已有明确对应关系提供细分主题入口，例如芯片→存储芯片／先进封装、机器人→人形机器人／减速器、人工智能→AI智能体／AI应用。映射为有限人工展示规则，不宣称完整产业链，也不把子主题外股票擅自纳入父主题；子主题始终按原始实际成员计算。

- **个股主展示主题**：先采用小范围行业匹配规则（如元件→PCB／MLCC），再优先具体主题并按候选涨停、事件及加权聚集选择。匹配只在该股原有概念内进行；保存`display_theme_basis`，不能把展示主题当作当日涨停原因。详情明确显示“今日交易逻辑未确认”，当前筛选主题优先露出。

## 十九、正式版可行性审查与当前落差（2026-09-15）

### 结论与定位

正式版可以在TickFlow QuantAll内实现为与QuantX平级的一级面板，建议路由为`/stock-pools`，顶层只保留“今日工作台／完整候选”。仓库已经具备一级导航扩展、FastAPI路由、Market Facts、Repository、盘后调度、React、TanStack Query、虚拟表格、个股预览和AI Provider；页面和交互本身不是主要风险。正式工程的核心是把Demo使用的临时输入改造成可从正式Repository独立重建、按日冻结和失败降级的数据产品。

当前Demo验证了产品结构和0914单日数据效果，不等于正式更新链已经完成。粗略成熟度如下：

| 部分 | 当前成熟度 | 主要缺口 |

### 不能直接沿用到正式版的Demo路径

以下路径只作为原型证据保留，不进入正式页面运行时：

- `scripts/build_stock_pool_daily_inputs.py`依赖`data/research/stock-pools/*/v1/daily-ledger.parquet`和上一交易日检查点，不能保证冷启动或任意日期重建；
- `scripts/build_stock_pool_panel_prototype.py`直接读取`data/quantx/<date>/*.json`、研究账本、命令行人气JSON和最新ext_data；
- `scripts/collect_stock_pool_popularity.py`直接导入`D:/quantall`内的采集适配器；
- `scripts/stock_pool_smnc.py`直接遍历外部QuantX Research目录；
- 最新概念成分快照只能作为当前静态关联代理，不能无提示地回填历史交易日。

这些脚本可继续作为规则对照和迁移验收样本，但正式API只允许调用StockPoolService／Repository，不保留“找不到正式事实就回读Demo文件”的隐式后备。

### 正式后端模块

建议新增独立的`backend/app/stock_pools/`领域模块，职责保持小而明确：

```text
rules.py             九个版本化候选生产器
events.py            事件锚点、年龄、有效期和失效判断
stages.py            主阶段及状态标签纯函数
aggregator.py        同股多来源合并、题材和优先层级
schemas.py           日期汇总、候选行和详情契约
repository.py        日期快照只读接口
publisher.py         校验、manifest和原子发布
service.py           API用例编排，不访问供应商数据
```

九池可以复用现有策略引擎的批量行情计算和共同指标，但候选生产器的输出语义是“召回理由”，不强制附会成买入、卖出或仓位策略。现有`screening_candidate_daily`继续服务通用规则筛选；股票池多来源事件、锚点、阶段和过期原因使用专用派生快照，以免破坏QuantX现有消费者。

### 正式API与前端

建议第一版提供三个主要只读接口：

```text
GET /api/stock-pools/{date}
GET /api/stock-pools/{date}/candidates
GET /api/stock-pools/{date}/candidates/{symbol}
```

第一个返回日期、来源质量、题材卡、阶段地图、变化汇总和规则版本；第二个返回完整候选的紧凑行并支持页面筛选；第三个按需返回来源事件、当日解释、静态关联、热榜和Research证据。这样无需一次传输整份详情，也不把409只股票的长文本提前装入工作台。

前端采用一级`/stock-pools`路由，与QuantX平级；复用现有日期选择、`StockDataTable`虚拟表格、`StockPreviewDialog`、加载／空／错误／陈旧／降级状态和统一API客户端。当前研究实施文档中“在QuantX下增加候选池页面”和窄屏卡片要求已经过时：正式第一版按当前决定实现平级导航和桌面端，不将手机端作为验收范围。

### 每日发布与恢复

股票池任务接在行情及QuantX Market Facts成功发布之后，自动任务与手动刷新调用同一入口：

```text
行情与enriched完成
  -> 通用外部来源及Market Facts完成
  -> 九池确定性计算
  -> 人气、题材和Research批量增强
  -> 与上一同版本快照比较
  -> 契约和来源质量校验
  -> 原子发布StockPoolSnapshot
  -> 清理查询缓存
```

支持三条恢复路径：本地`recompute`不访问网络；可选来源补采后重建同日快照；可选来源失败时以`degraded`发布可用结果。构建失败继续保留上一份有效快照。跨日新增、退出和阶段迁移只在基础过滤、召回规则版本及关键来源覆盖可比时生成，否则返回明确不可比较原因。

### LLM接入边界

LLM能力复用现有AI Provider，放在每日构建阶段并按输入指纹缓存，不在页面请求时逐股即时调用。第一版只用于题材同义归一、逐股角色提取、证据摘要和矛盾提示；输出必须保留来源item ID、观察时间、模型／提示版本和置信状态。LLM失败时仍发布确定性九池、原始题材证据和静态关联，不能影响召回资格、阶段和基础过滤。

### 个人状态

单机第一版可继续使用localStorage，但键必须包含交易日、代码和候选信号指纹，防止规则或证据变化后错误继承“已看／暂不关注”。需要跨设备或长期统计时，再接入`user_data`下的通用用户状态Repository和API；它不阻塞股票池正式版首发。

| 阶段 | 预估 |
| --- | ---: |
| 九池正式计算器、锚点和有效期 | 5—8人日 |
| 股票池快照、Repository和API | 4—6人日 |
| React正式页面 | 4—6人日 |

先完成“八池确定性数据→快照→API→React页面”，即可得到可每日使用的正式MVP；随后接入多源人气、题材证据、SMNC和LLM增强。可用MVP约2—3周，完整版本约4—6周。最大不确定性是网页型人气和当日题材来源的稳定性，前端实现本身风险较低。

正式完成标准：任一页面数字能追溯到Repository和来源快照；相同输入与规则版本可重建相同结果；单一可选来源失败不会阻断发布；历史页面不会使用未来材料或最新概念静默回填；前端不计算召回、阶段和题材业务规则；Demo文件和外部项目目录不属于生产运行依赖。
